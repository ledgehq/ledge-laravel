# Release Notes for Ledge for Laravel

## 1.0.2 - 2026-10-22
- Fixed: the `environment` check reported every `env('X')` call in `config/` without a default as a missing variable, which on a stock Laravel app flagged dozens of optional services (`AWS_ENDPOINT`, `PUSHER_APP_KEY`, `MEMCACHED_*`, ...) and, once the config was published, the package's own `LEDGE_*` options. `.env.example` is now the only declaration: keys with a value are required and reported under `missing`, blank keys are optional and reported under `optional` without affecting the status, and `LEDGE_*` is never reported. New `source` field (`.env.example` or `null`) says where the expectations came from

## 1.0.1 - 2026-10-22
- The `packages` check now reports `frameworkVersion.installed` from the running application on every poll, including before the first `ledge:packages:refresh`; `latest` and `updateAvailable` still come from the Packagist snapshot

## 1.0.0 - 2026-10-22
- Added checks: `cache` (roundtrip on the default store), `redis` (`PING`, only when cache/queue/session/broadcasting use Redis), `horizon` (master supervisor state plus supervisor, process, wait-time, and recent-failure figures, only when Horizon is installed; the `queue` check notes when staleness is not observable on its driver), `optimized` (config/route/event caches, enforced in production), `phpVersion` (support phase from php.net's calendar), and `packages` (outdated Composer packages with a `frameworkVersion` entry, read from the snapshot `ledge:packages:refresh` stores; scheduled daily unless `packages_auto_refresh` is off). Each has a status option: `cache_failure_status`, `redis_failure_status`, `horizon_stopped_status` / `horizon_paused_status`, `not_optimized_status`, `php_security_only_status` / `php_eol_status`, `update_available_status`
- Custom checks can be listed as class names under `checks` in `config/ledge.php`, registered inline with `Ledge::check('name', fn () => ...)`, or wrapped from spatie/laravel-health with `SpatieHealthCheck::wrap()`. A listed class that cannot be built is logged and skipped rather than breaking the health endpoint
- Requires PHP 8.3+ and Laravel 13+ (Laravel 11 and 12 are no longer targeted)
- Added the acquire capability with the `backup` profile: `POST /_ledge/acquire` accepts Ed25519-signed commands (keys discovered from the Ledge keyset, permanent pins, replay guard, host allowlist) and dispatches a `BackupJob` that dumps the default database connection through `spatie/db-dumper`, gzips, seals the archive to the command's `bundle_pubkey`, streams it to `upload_url`, and reports progress through bearer-authenticated callbacks; `GET /_ledge/acquire/{runId}` is the pull fallback. Off by default (`LEDGE_ACQUIRE_ENABLED`); profiles are a registry on `AcquireService` so a platform layer can add `full`. See `docs/acquire-protocol.md`
- The health payload now reports real `acquireEnabled` / `backupProfileSupported` values plus `capabilities` (registered profiles) and `updateTest: {strategy: "testsuite"}`
- The shared-key middleware rejects the query-parameter key on acquire routes regardless of `allow_query_key`, and answers there with `{accepted: false, reason: "invalid_key"}`
- Initial scaffold: key-authenticated `GET /_ledge/health` and `GET /_ledge/dependencies`, `ledge:generate-key`, and the `database`, `queue`, `disk`, `memory`, `debugMode`, `environment`, `storage`, `scheduler`, and `failedLogins` checks. Payload shape and `dependenciesHash` normalization match the Craft plugin
