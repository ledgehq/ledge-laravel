# Release Notes for Ledge for Laravel

## 1.3.1 - 2026-11-25
- Supports `guzzlehttp/guzzle` `^8.0` alongside `^7.8`, so the package installs in apps that have moved to Guzzle 8. Behavior, retry classification and the acquire payload are unchanged on Guzzle 7. On Guzzle 8 the upload reads the response carried by an exception from `ResponseException` (Guzzle 8 removed `RequestException::getResponse()`), and `curl_errno` from the transfer stats' handler error data instead of the exception's handler context, which Guzzle 8 removed. With the curl handler the errno is the same on both majors; with any other handler it is `null`, as it already was on Guzzle 7
- On Guzzle 8 the exception type in an upload attempt's `error` and in the reason line is Guzzle 8's class name, which is more specific than Guzzle 7's: a timeout reads `NetworkTimeoutException curl 28` (or `ConnectTimeoutException`, or `ResponseTimeoutException` once the response headers had arrived) where Guzzle 7 gives `ConnectException curl 28`, and a transfer failure after the headers reads `ResponseTransferException` instead of `RequestException`. The longer names leave a little less of the 200-byte `error` for the message. Keys, types, statuses, redaction and the 255-character reason limit are unchanged, and Ledge never reads the type (it matches `upload_failed` by prefix). Guzzle 8 also defaults the curl connect timeout to 60s (Guzzle 7: libcurl's 300s), so a connect that hangs now fails sooner and is retried like any other timeout
- CI runs the suite, Pint and PHPStan on Guzzle 7 and 8

## 1.3.0 - 2026-11-24
- **Behavior change:** the acquire bundle upload is retried instead of failing the run on the first error, for every profile. Transport failures with no response (connect errors, resets, timeouts) and HTTP `408`, `429`, `500`, `502`, `503` and `504` are retried, up to 5 attempts in all, waiting 2s, 6s, 18s and 54s, each with ±25% jitter (about 80s in all); a longer `Retry-After` (seconds or HTTP-date) is honoured up to 60s. `413` (`bundle_too_large`), `409` (`run_already_finished`) and every other status, including `403` and `501` (`upload_failed`), stay terminal with the same reason codes. Each attempt reopens the already-encrypted bundle and sends the whole body with the same `Content-Length`; nothing is re-dumped or re-encrypted. The job still runs once (`tries = 1`); the retries happen inside the upload step, and the waits go through Laravel's `Sleep`, so `Sleep::fake()` skips them in tests
- Retries fit inside the upload URL's validity: `AbstractAcquireJob` takes a trailing optional `acceptedAt` constructor argument (default `0`), which `AcquireService` sets when it dispatches the job; no retry starts at or after accepted + 55 minutes (`AbstractAcquireJob::UPLOAD_DEADLINE_SECONDS`), and each attempt's timeout is clipped to `max(30s, min(600s, time left))`. Jobs queued by 1.2.0 unserialize with `acceptedAt` `0` and upload without the deadline; a profile job built with the previous six arguments does the same. Independently, no new attempt starts once the time since the first one began would exceed 600s. A run that gives up says why in its `detail`, e.g. `upload target responded with HTTP 503 after 5 attempts`
- Added `acquire.upload_retried` (step `upload`), sent before each retry wait with `{reason, max_attempts, retry_in_ms, upload_attempts, upload_attempt}`; a failed or throwing callback neither fails the job nor uses up an attempt. `acquire.failed` is still sent once, after retries are exhausted or on a terminal status. `reason` is a one-line summary of the attempt, always under 255 characters (`attempt 2/5: HTTP 503 SlowDown, request-id abc123, 412 ms, sent 0/26214400 bytes, retry-after 1`), since `detail.reason` is what Ledge stores as the event's reason; `upload_attempt` is the attempt that just failed, `{attempt, started_at, status, error, curl_errno, error_code, request_id, request_ids, retry_after, duration_ms, bytes_sent, remote_ip, body, retry_in_ms}`, with the S3 `<Code>` parsed from the body, request-id headers only (`x-amz-request-id`, anything containing `request-id` or `amz-id`, `cf-ray`; at most 5) and at most 300 bytes of a non-2xx body. Each event carries one attempt, never the history: Ledge keeps at most 1500 bytes of an event's other `detail` keys after bounding and drops all of them past that, so the package keeps that part under 1400 bytes, shedding the attempt's `body`, then `request_ids`, then cutting `error` and `detail` to 120 characters when a worst-case attempt would not fit (a typical S3 `503 SlowDown` attempt fits whole)
- **Behavior change:** an `upload_failed` `acquire.failed` now has `reason` `upload_failed: <summary of the last attempt>` (e.g. `upload_failed: attempt 5/5: HTTP 503 SlowDown, …`) instead of the bare code; Ledge matches `upload_failed` by prefix. Every other code, including the upload step's `bundle_too_large` and `run_already_finished`, keeps the bare code as `reason`, and the status endpoint still records the bare code. Every `acquire.failed` gains `reason_code` with the bare code and whichever of `dump_duration_ms`, `encrypt_duration_ms` and `upload_duration_ms` had been measured, plus `peak_memory_bytes`; a failure at the upload step adds `upload_attempts` and `upload_attempt` (the last attempt, absent when none was made)
- `acquire.completed` (every profile, from the shared pipeline) keeps its existing keys and adds `encrypt_duration_ms`, `upload_duration_ms`, `upload_attempts` (int) and `peak_memory_bytes`; earlier failed attempts of a run that then succeeded were reported by their own `acquire.upload_retried` events
- Fixed: a transport error during the upload put Guzzle's message, which ends with the full signed `upload_url` including its signature, into the `acquire.failed` `detail` and the app log. The URL is now reduced to scheme, host and path everywhere it could appear, and its query string and long values, the callback token and the bundle public key are replaced with `[redacted]` in echoed headers, bodies and messages
- `AcquireException` takes an optional fourth `context` array (the upload carries its `UploadDiagnostics` in `context['upload']`); `BundleUploader::upload()` returns `UploadDiagnostics` and accepts a retry hook, a deadline and extra secrets to redact. Same change as the Craft plugin's 5.14.0 / 4.14.0

## 1.2.0 - 2026-11-10
- **Behavior change:** the `phpVersion` check's defaults now follow the time left before end of life instead of the support phase. `php_security_only_status` defaults to `healthy` (was `degraded`) and `php_eol_degraded_within_days` to `180` (was `null`, off); `php_eol_status` (`unhealthy`) and `php_eol_unhealthy_within_days` (`90`) are unchanged. With the defaults a security-only branch is healthy until 180 days before end of life, degraded from 180 days, unhealthy from 90 days, and unhealthy once past end of life. Previously a site went degraded the day active support ended and stayed there for the two years of security fixes; PHP 8.3, for example, now stays healthy until 2027-07-03 and turns degraded on 2027-07-04. Apps that set either option, in `config/ledge.php` or through `LEDGE_PHP_SECURITY_ONLY_STATUS` / `LEDGE_PHP_EOL_DEGRADED_WITHIN_DAYS`, keep their configured behavior; set `php_security_only_status` to `degraded` and `php_eol_degraded_within_days` to `null` to restore the previous defaults. **An app that has published `config/ledge.php` keeps the old defaults**, since the published file carries `env('LEDGE_PHP_SECURITY_ONLY_STATUS', 'degraded')` and `env('LEDGE_PHP_EOL_DEGRADED_WITHIN_DAYS')`; change those two defaults to `'healthy'` and `180` to adopt the new behavior. The check's meta is unchanged: `phase`, `activeSupportUntil`, `securitySupportUntil`, `daysUntilEol` and `thresholds` are still reported. Same change as the Craft plugin's 5.12.0 / 4.12.0

## 1.1.1 - 2026-11-10
- Removed `backupProfileSupported` from the health payload. The Ledge service reads `capabilities` (`["backup"]` while acquire is on, `[]` while off) whenever it is present, so the boolean carried nothing it uses. `acquireEnabled` stays

## 1.1.0 - 2026-11-10
- The `phpVersion` check now trips when the running branch is close to end of life, whatever its phase: `php_eol_unhealthy_within_days` (default `90`, `LEDGE_PHP_EOL_UNHEALTHY_WITHIN_DAYS`) and `php_eol_degraded_within_days` (default `null`, off, `LEDGE_PHP_EOL_DEGRADED_WITHIN_DAYS`) count days until the branch's security support ends, inclusive. The worse of this and the phase status wins. Adds `daysUntilEol` to the check's meta (`null` for an unknown or end-of-life branch) and both values to `thresholds`; same shape as the Craft plugin's 5.10.0. Set `php_eol_unhealthy_within_days` to `null` to keep the previous behavior
- The check now catches its own failures and reports `degraded` with "Check unavailable", like the other checks
- Documented running the acquire job on a dedicated queue listed first on the worker, since Laravel queues have no job priority (the Craft plugin's `acquireJobPriority` counterpart)

## 1.0.2 - 2026-10-22
- Fixed: the `environment` check reported every `env('X')` call in `config/` without a default as a missing variable, which on a stock Laravel app flagged dozens of optional services (`AWS_ENDPOINT`, `PUSHER_APP_KEY`, `MEMCACHED_*`, ...) and, once the config was published, the package's own `LEDGE_*` options. `.env.example` is now the only declaration: keys with a value are required and reported under `missing`, blank keys are optional and reported under `optional` without affecting the status, and `LEDGE_*` is never reported. New `source` field (`.env.example` or `null`) says where the expectations came from

## 1.0.1 - 2026-10-22
- The `packages` check now reports `frameworkVersion.installed` from the running application on every poll, including before the first `ledge:packages:refresh`; `latest` and `updateAvailable` still come from the Packagist snapshot

## 1.0.0 - 2026-10-22
- Added checks: `cache` (roundtrip on the default store), `redis` (`PING`, only when cache/queue/session/broadcasting use Redis), `horizon` (master supervisor state plus supervisor, process, wait-time, and recent-failure figures, only when Horizon is installed; the `queue` check notes when staleness is not observable on its driver), `optimized` (config/route/event caches, enforced in production), `phpVersion` (support phase from php.net's calendar), and `packages` (outdated Composer packages with a `frameworkVersion` entry, read from the snapshot `ledge:packages:refresh` stores; scheduled daily unless `packages_auto_refresh` is off). Each has a status option: `cache_failure_status`, `redis_failure_status`, `horizon_stopped_status` / `horizon_paused_status`, `not_optimized_status`, `php_security_only_status` / `php_eol_status`, `update_available_status`
- Custom checks can be listed as class names under `checks` in `config/ledge.php`, registered inline with `Ledge::check('name', fn () => ...)`, or wrapped from spatie/laravel-health with `SpatieHealthCheck::wrap()`. A listed class that cannot be built is logged and skipped rather than breaking the health endpoint
- Requires PHP 8.3+ and Laravel 13+ (Laravel 11 and 12 are no longer targeted)
- Added the acquire capability with the `backup` profile: `POST /_ledge/acquire` accepts Ed25519-signed commands (keys discovered from the Ledge keyset, permanent pins, replay guard, host allowlist) and dispatches a `BackupJob` that dumps the default database connection through `spatie/db-dumper`, gzips, seals the archive to the command's `bundle_pubkey`, streams it to `upload_url`, and reports progress through bearer-authenticated callbacks; `GET /_ledge/acquire/{runId}` is the pull fallback. Off by default (`LEDGE_ACQUIRE_ENABLED`); profiles are a registry on `AcquireService` so a platform layer can add `full`. See `docs/acquire-protocol.md`
- The health payload now reports real `acquireEnabled` / `backupProfileSupported` values plus `capabilities` (registered profiles) and `updateTest: {strategy: "testsuite"}`
- The shared-key middleware rejects the query-parameter key on acquire routes regardless of `allow_query_key`, and answers there with `{accepted: false, reason: "invalid_key"}`
- Initial scaffold: key-authenticated `GET /_ledge/health` and `GET /_ledge/dependencies`, `ledge:generate-key`, and the `database`, `queue`, `disk`, `memory`, `debugMode`, `environment`, `storage`, `scheduler`, and `failedLogins` checks. Payload shape and `dependenciesHash` normalization match the Craft plugin
